## 1. Purpose

Define the common identifier rules used by every module before any module persists data. No module may create its own identifier format, generation strategy, or identity semantics.

This contract covers three distinct identifier families:

1. **Internal entity identifier** — identity of a persisted entity.
2. **Operation identifier** — identity of a confirmation that creates facts or movements.
3. **External migration key** — identity of a record imported from another system.

## 2. Scope and non-goals

This contract defines formats, generation responsibilities, scope, preservation rules, and validation expectations. It does not define the wire format of APIs or error responses.

The following concerns remain owned by other contracts:

- Login identifier rules remain in C-02 and VAL-11.
- Human-readable catalog codes for item, category, unit, and numbering remain in TG-01-02, but they must not replace internal identifiers.
- The public error envelope and error codes remain in C-01 item 2.
- Transport details, headers, and endpoint shapes remain in C-01 item 3.
- The Bússola export format remains pending under LAC-11. This contract defines the internal key structure, not an invented source format.

## 3. Internal entity identifier

### 3.1 Format

- Canonical representation: UUID string, lowercase, hyphenated, 36 characters.
- Proposed version: **UUIDv7** (RFC 9562), because it is globally unique and time-ordered.
- Alternative if UUIDv7 is rejected: UUIDv4. The team must record the decision before implementation.
- Persistence: PostgreSQL `uuid` type.
- API representation: JSON string in canonical form.

### 3.2 Generation

- Generated once, server-side, when the entity is created.
- Never generated from CPF, name, date, sequence, or any business attribute.
- Never reused, including after deletion or cancellation.
- Client-supplied entity identifiers are rejected in normal create operations.

### 3.3 Semantics

- The identifier is opaque and has no business meaning.
- It is immutable for the lifetime of the entity.
- It is the canonical reference for foreign keys, history, audit, reports, and imports.
- It is not an authorization mechanism. Every access still requires server-side authorization per RF-ACS-03.
- CPF must never be used as a counting or identity key (RF-REL-03).

### 3.4 Validation

- Reject malformed identifiers at the application boundary.
- Do not silently coerce, truncate, or normalize an invalid identifier.
- A missing required reference is invalid; absence must not become a zero, empty string, or fictitious entity (VAL-07, VAL-12).

## 4. Operation identifier

### 4.1 Format

- Canonical UUID string, lowercase, hyphenated.
- Accepted versions: UUIDv4 or UUIDv7. UUIDv4 is acceptable for client-generated retries using the Web Crypto API.
- The transport binding is defined by C-01 item 3.

### 4.2 Generation and scope

- Generated by the client for each logical confirmation that creates facts or movements.
- Reused unchanged when the same operation is retried.
- A new logical operation requires a new identifier, even when the data is identical.
- Uniqueness is enforced within the authorized operation scope, not globally across unrelated actors.
- The same identifier in a different authorized scope must not return another actor's result.

The authorized operation scope contains at least the operation type and the authenticated actor. The exact scope representation is defined by C-01 item 3.

### 4.3 Required operations

At minimum, an operation identifier is required for confirmations that create:

- attendance records;
- frequency records;
- stock entries and exits;
- deliveries and reversals;
- Bazar transfers;
- import batches and imported facts.

### 4.4 Idempotency semantics

For the same operation identifier and the same authorized scope:

- Same normalized content: return the previously stored result without creating new effects.
- Different normalized content: reject with an explicit conflict; do not overwrite or partially apply.
- Response lost after persistence: the client retries with the same identifier; the server returns the stored result.
- Two legitimate operations with identical business data must have different identifiers.

The normalized content and conflict representation are defined by C-01 items 2 and 3. The server must store enough information to distinguish replay from conflict.

### 4.5 Persistence expectations

The operation record must preserve at least:

- operation identifier;
- authorized scope;
- operation type;
- normalized content reference or digest;
- result reference;
- actor and timestamp from the authenticated context.

The operation identifier is not an entity identifier and must not be used as a primary key for business entities.

## 5. External migration key

### 5.1 Composite identity

Each imported record is identified by the composite key:

`(sourceSystem, recordType, externalId)`

- `sourceSystem`: stable code for the source system.
- `recordType`: controlled value describing the imported record type.
- `externalId`: stable identifier supplied by the source system.

### 5.2 Preservation rules

- Preserve the external identifier exactly as exported, including leading zeros, case, accents, and punctuation.
- Do not use CPF, name, or family number as a substitute for the external key.
- Do not normalize the identifier in a way that changes identity.
- An optional normalized form may exist for search only; identity always uses the original value.
- Length limits must be explicit and enforced; over-limit values are rejected, never truncated (VAL-12).

### 5.3 Batch metadata

Batch identifier, import timestamp, and execution number are metadata. They are not part of the record identity.

Re-executing a different batch with the same composite key:

- same content: no duplicate record;
- divergent content: explicit conflict, no automatic merge;
- no stable external key: block the import until a mapping is defined and reviewed.

### 5.4 Internal mapping

Every imported record receives a new internal entity identifier. The mapping between the external key and the internal identifier must be persisted so re-execution and traceability remain possible.

## 6. Human-readable codes

Human-readable codes for catalogs, items, categories, units, and numbering are separate from internal identifiers.

- They may be displayed to users.
- They must be unique within their defined scope.
- They must be immutable once used by a persisted fact or movement.
- They must never replace the internal identifier in relationships, reports, or audit records.
- Their exact format belongs to TG-01-02.

## 7. Cross-cutting rules

- Internal identifiers are opaque; never derive business decisions from their value.
- Identifiers do not grant access; authorization is always enforced on the server.
- Audit records reference internal identifiers and the operation identifier where applicable.
- Logs may contain identifiers for correlation but must not expose sensitive personal data.
- No module creates a parallel identifier scheme.
- No identifier is silently recycled after deletion, cancellation, or reversal.

## 9. Open points requiring agreement

Recommended positions for the C-01 base review:

1. **UUIDv7 versus UUIDv4 for internal IDs.** Recommend UUIDv7; use UUIDv4 only if runtime or library support is insufficient. Owner: Alan and the reviewers.
2. **Operation ID availability.** Recommend requiring UUIDv4 from the Web Crypto API; confirm supported clients. Owner: Felipe and the frontend workstream.
3. **External ID normalization.** Recommend preserving the original value exactly; block import when LAC-11 does not confirm a stable key. Owner: Alan, with LAC-11.
4. **Catalog codes.** Recommend keeping catalog codes separate and aligning them with TG-01-02 (Erick).
